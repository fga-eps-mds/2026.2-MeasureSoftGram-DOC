## 3. Problemas do banco (Marcos)

### O que foi encontrado

- A função do service que busca os últimos valores calculados de característica (arquivo de jobs, linhas 74 a 85) **não filtra por repositório**.
- Exemplo: o usuário analisa o repositório A, depois analisa o B e, por fim, volta ao A para fechar a release. Nesse momento, a função pega a nota mais recente de **qualquer** repositório, não a do A.
- O Marcos demonstrou isso com uma consulta direta no banco: a nota usada só sai certa quando o último repositório analisado é o próprio.
- A tabela de análise tem uma chave opcional solta, o que abre espaço para esse tipo de erro.
- Esse bug afeta o objetivo central do produto, que é calcular a nota do repositório.

### Outros problemas estruturais

- O modelo do banco não atende ao que o produto precisa. Os jobs gravam dados de forma atípica.
- As métricas de todos os arquivos são salvas a cada PR, sem limite. Em produção, isso não escala.
- Os valores calculados podem divergir entre o CLI, que roda local e é a fonte da verdade, e o Service, que usa o banco.

### Decisão

- **Corrigir agora o cálculo errado.** Uma dupla resolve em uma semana; o Marcos confirmou o prazo, mas a solução ainda precisa ser aprovada.
- A correção deve ficar contida no service, mantendo o mesmo contrato da função ou do endpoint, para não causar regressão no front nem nos plugins.
- Verificar se o mesmo problema acontece nos outros níveis (subcaracterística e métrica).
- Os problemas estruturais do banco e dos jobs **não serão resolvidos neste semestre**. Eles vão para a documentação do pós-morte, com um caminho sugerido.
- Na quarta, o time avisa o PO com o impacto no produto e no que já foi desenvolvido.

## 4. Entrega contínua entre repositórios (Luciano)

### Diagnóstico

- O projeto tem vários repositórios que dependem uns dos outros. O Core é usado pelo Service e pelo CLI, junto com o Parser. Action, Front e AI chamam a API do Service.
- A versão do Core é fixada manualmente em cada repositório que depende dele, e as versões release candidate não são puxadas automaticamente. No início do semestre havia três versões do Core rodando ao mesmo tempo.
- Isso gera três problemas:
  - **Quebra de confiabilidade:** o CLI e o Service chegam a resultados diferentes.
  - **Custo operacional:** cada atualização exige PRs manuais em cada repositório.
  - **Atraso de feedback:** uma mudança no Core só mostra impacto no CLI ou no Service bem depois.
- O Dependabot já está atualizando seis repositórios.
- A ideia inicial é usar *repository dispatch*. A dúvida é que isso gera novas versões de pacote mesmo sem mudança no código.

### Discussão

- O Luciano defende que isso é mais crítico do que adicionar a característica de segurança, porque o cálculo já ficou errado entre semestres e há usuários usando o produto.
- O Lucas propôs usar o repositório Platform para centralizar o dispatch e o deploy.
- A Luiza pediu para delimitar exatamente o que o PO considera crítico. Sem essa delimitação, o escopo não para de crescer e o time não tem argumento para priorizar nem para retirar outra coisa do escopo.
- O Alexandre alertou que mudar o fluxo de deploy com apenas uma release restante é arriscado, porque não sobra tempo para corrigir se der errado.

### Recorte acordado

| Problema | Solução proposta | Prazo estimado |
| --- | --- | --- |
| Versões desatualizadas entre repositórios | Documentar e validar os passos manuais e, se possível, empacotar como uma skill para agente de IA executar | 1 sprint |
| Regressão entre repositórios | Smoke tests no repositório Platform, integrados ao CI, só para Core, Parser e CLI. Deixar estruturado para os próximos semestres | cerca de 2 semanas |

- O Luciano monta o **plano de execução** com base nesse recorte e envia no grupo antes da quarta. O time decide se ele entra no escopo da R3.

## 6. Fluxo de validação e2e (vale a partir de agora)

- O PO não vai mais usar formulário de aceitação. A validação passa a ser feita por **teste e2e a partir do front**.
- **Escopo inicial:** cobrir, critério por critério, as 10 US que já têm código no front. O esforço estimado é de 7 a 9 dias de uma pessoa. A Luiza entrega até sexta (13/11).
- **Como funciona:**
  - O teste abre o front de verdade, com uma sessão simulada, num ambiente isolado. Ele não depende da VM.
  - Cada critério de aceitação vira um cenário com passo a passo.
  - Os testes rodam em todo PR.
  - O relatório fica disponível por 30 dias no Actions. Uma automação anexa o resultado na issue da US de origem.
  - Antes de abrir o PR, o teste deve rodar 3 vezes localmente para detectar instabilidade.
- A US 21.3 já está no repositório como exemplo.
- A Luiza vai subir um template com passo a passo e uma skill que gera os cenários a partir dos critérios de aceitação.
- **A definir pelo time, na doc:** se o teste e2e entra no mesmo PR da US ou num PR separado.
- A US 14 ainda não tem critério de aceitação, por isso não tem teste.
