# História de Usuário

Template e boas práticas para escrita e refinamento de Histórias de Usuário (US)
na disciplina, com base no acordo firmado na [reunião de 23/09](/docs/reunioes/reunioes-po/ata-po-23-09).

## Estrutura padrão

Toda história deve seguir o formato:

> **Como** [persona do produto],\
> **Quero** [ação / funcionalidade],\
> **Para que** [benefício / valor de negócio gerado].

## Diretrizes de escrita

- Escrita **pelo ponto de vista do usuário final** (o PO ou a persona definida).
- Critérios de aceitação escritos em formato de cenários **BDD (Given/When/Then)**, cobrindo o caminho feliz e ao menos um
  cenário de exceção.
- Critério de aceitação (o **quê**, negócio) separado de critério técnico (o **como**).
- Correção de defeito existente **não** é US: abra um bug
  (diretriz do PO, [ata de 23/09](/docs/reunioes/reunioes-po/ata-po-23-09)).

## DoR — pronta para entrar na sprint

- [ ] Persona identificada e coerente com a visão de produto.
- [ ] Critérios de aceitação em BDD validados pelo PO.
- [ ] Protótipo no Figma aprovado (para telas novas ou alteradas).
- [ ] Dependências técnicas mapeadas.
- [ ] Estimativa em Story Points realizada na planning.

## DoD — pronta para ser considerada entregue

- [ ] Código implementado e funcional em homologação (`develop`).
- [ ] Testes unitários com cobertura ≥ 85% no repositório.
- [ ] Pipeline de CI verde (lint, build, testes, SonarCloud).
- [ ] Documentação técnica e de usuário atualizada.
- [ ] PR revisado e aprovado por pelo menos um membro de outro squad.
- [ ] Teste de aceitação executado e validado pelo PO.
