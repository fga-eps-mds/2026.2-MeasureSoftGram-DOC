# Fluxo de Trabalho

Como a equipe MeasureSoftGram organiza o ciclo de vida do código, das issues aos
deploys em produção, integrando os repositórios forks do semestre e os
repositórios centrais.

## 1. Do issue ao desenvolvimento

1. Toda atividade começa em uma **issue** no repositório correspondente (ou no
   DOC para gestão).
2. O desenvolvedor atribui a si mesmo a issue e a move para a coluna **In
   Progress** no Zenhub.
3. Cria uma branch a partir de `develop` seguindo a convenção:
   - `feat/nome-da-feature` para novas funcionalidades;
   - `fix/nome-do-bug` para correção de defeitos;
   - `docs/nome-do-documento` para documentação;
   - `refactor/nome-da-refatoracao` para melhorias de código sem impacto externo.

## 2. Padrão de commits

Adotamos [Conventional Commits](https://www.conventionalcommits.org/):

- `feat:` nova funcionalidade para o usuário;
- `fix:` correção de bug;
- `docs:` alterações exclusivamente em documentação;
- `test:` adição ou correção de testes;
- `refactor:` refatoração que não corrige bug nem adiciona funcionalidade;
- `chore:` tarefas de manutenção, dependências e build.

## 3. Qualidade antes do pull request

Antes de abrir o PR, execute localmente:

- Lint do código (`npm run lint` ou `flake8` / `black`);
- Suíte de testes unitários;
- Verifique se a cobertura não caiu abaixo de 85%.
- Uso relevante de IA: registre no PR e no seu `MD_Template.md`
  ([Uso de IA na equipe](/docs/equipe/uso-de-ia)).
- Evite *squash* sem necessidade: o histórico é evidência de autoria e permite rollback
  (acordo da [reunião de 02/09](/docs/reunioes/reunioes-po/ata-po-02-09)).

## 4. Pull request

- Todo PR deve ter título descritivo e seguir o template do repositório.
- Aponte o PR para a branch `develop` do repositório central.
- É obrigatório ter pelo menos **uma aprovação de outro integrante** antes do merge.
- O pipeline de CI deve passar integralmente (lint, testes, SonarCloud).

## 5. Ambientes e deploy

- **Homologação (`develop`):** deploy automático da branch `develop` dos repositórios
  centrais na VM de testes.
- **Produção (`main`):** promoções periódicas de `develop` para `main` mediante
  criação de release tags e validação pelo PO.
